# cracktunes metrics (v0.48.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** cracktunes serves Prometheus metrics on its own port when `METRICS_BIND` is set, covering health, commands, playback, per-server usage and every fallback.

**Architecture:** A new leaf crate `crack-metrics` owns every metric name, every label value (as enums) and one function per event, on top of the `metrics` facade. Other crates call those functions and nothing else. `crack-cli` installs the Prometheus recorder and its HTTP listener at start-up; with no recorder installed every call is a no-op. A 15-second sampler in `crack-core` sets the gauges and advances the per-server time counters.

**Tech Stack:** Rust; `metrics` 0.24, `metrics-exporter-prometheus` 0.18, `metrics-util` 0.20 (dev, debugging recorder), `metrics-process` 2.4; tokio; serenity/poise/songbird as already pinned.

**Spec:** `docs/superpowers/specs/2026-11-25-metrics-and-monitoring-design.md` (Part 1). Part 2 (homelab) is a separate plan.

## Global Constraints

- Metric prefix `cracktunes_`. Names, types and label sets exactly as in the spec's tables, except the two deviations below.
- **Never a label:** track title, URL, search query, user id, channel id, error text. `guild_id` appears only on the five `cracktunes_guild_*` metrics.
- No crate other than `crack-metrics` writes a metric name string or calls a `metrics::` macro.
- A metrics failure never reaches a command: event functions return `()`, a listener that cannot bind logs one ERROR line and the bot continues.
- `METRICS_BIND` unset: no recorder, no listener, one INFO line `metrics off`. Set: one INFO line `metrics on <addr>`.
- The endpoint is `GET /metrics` on its own listener, never a route on the `crack-web` dashboard. No token.
- Delete the `crack-metrics` cargo feature, the `prometheus` dependency, `crack-core/src/metrics.rs` and both `count_command` variants.
- Rust serialization rule (owner's global): no `serde_json::json!` / `Value` for data we own. Nothing here should need either.
- Run every local `cargo test` / `nextest` / `clippy` inside `systemd-run --user --scope --quiet -p MemoryMax=12G -p MemorySwapMax=0 -p OOMPolicy=continue -- bash <script>` (put the commands in a script file; `systemd-run` expands `$VAR`). Never `cargo clean`. Never `git add -A`; add files by name.
- Imports are explicit, no globs outside tests (clippy enforces it).
- Every commit ends with exactly this trailer and no other `Co-Authored-By`:
  `Co-Authored-By: Claude & Lothrop (cycle.five@proton.me)`
- Branch: `feat/metrics` (exists, holds the spec).

**Deviations from the spec (controller's calls, reported to the owner):**

1. `cracktunes_sleevenote_retries_total` is not built. `crack-sleevenote` is a published, dependency-free client and retries happen inside it. Instead the caller records `cracktunes_sleevenote_requests_total{outcome}` and a new `cracktunes_sleevenote_request_duration_seconds` histogram; a retried request shows as a slow one.
2. The `_seconds_total` counters are whole seconds, advanced by the 15-second sampler.

## Review Focus

1. `METRICS_BIND` holds something that is not a socket address (`9091`, `localhost:9091`, empty string) → one ERROR line naming the value, bot runs, nothing listens. (Task 1)
2. The port is already in use → same. (Task 1)
3. A server name containing `"`, `\`, a newline or emoji → `/metrics` still parses as valid exposition text. (Task 3)
4. An error message never seen before → `FailureReason::Other`, counted, and its text appears nowhere in `/metrics`. (Task 1)
5. A bot in no voice channel, just started → `cracktunes_gateway_connected`, `cracktunes_voice_connections`, `cracktunes_tracks_playing` and `cracktunes_queued_tracks` are present with value 0, not absent (the homelab alert on `gateway_connected == 0` depends on it). (Task 1 sets them at install; Task 3 keeps them set.)

```rust
// metrics_sampler.rs
pub const SAMPLE_EVERY: std::time::Duration = std::time::Duration::from_secs(15);

/// What one voice call looks like to the sampler. Built from songbird by `observe`, by hand in tests.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct CallSample { pub guild_id: u64, pub connected: bool, pub playing: bool, pub queued: usize }

/// Pure: turns one tick's samples into metric calls. `tick` is the time since the previous tick.
pub fn record(samples: &[CallSample], tick: std::time::Duration);
```

`record` rules: `voice_connections` = samples with `connected`; `tracks_playing` = samples with `playing`; `queued_tracks` = sum of `queued`; each `connected` sample adds `tick` whole seconds to `guild_voice_connected_seconds`; each `playing` sample adds `tick` whole seconds to `guild_playback_seconds`. A paused track is not `playing`.

Gateway: `Ready` → `gateway_event(Ready)`, `set_gateway_connected(true)`; `Resume` → `gateway_event(Resumed)`, `set_gateway_connected(true)`; `ShardStageUpdate` → connected is true only for the `Connected` stage, and a move away from `Connected` also counts `gateway_event(Reconnect)`. The sampler also sets `set_guilds(cache guild count)` and `set_gateway_latency` (from the shard runner's latency when it is known) each tick. `GuildCreate`/`GuildUpdate` → `set_guild_info(id, name)`.

### Task 5: Fallbacks

**Files:**
- Modify: `crack-music/Cargo.toml`, `crack-music/src/sources/proxy_fallback.rs`; `crack-types/Cargo.toml`, `crack-types/src/fallback.rs`; `crack-testing/Cargo.toml`, `crack-testing/src/suggested.rs`; the sleevenote call site in `crack-music/src/music/query.rs` (~663, `spotify_query` and what it calls)

**Interfaces — Consumes:** `proxy_fallback`, `ProxyOutcome`, `search_fallback`, `SearchFallbackReason`, `SearchFallbackOutcome`, `sleevenote_request`, `RequestOutcome`, `suggestion_label`, `SuggestionLabelOutcome`.

Rules:
- **Proxy fallback: once per gated track.** `ProxyFallback` gets a `reported: bool`. The `fail_over!` macro counts attempts as it loops and, the first time it finishes for this source, calls `proxy_fallback(outcome, attempts)` and logs one INFO line `proxy fallback {outcome} after {attempts} attempt(s)`: first success → `Recovered`; all `MAX_PROXY_ATTEMPTS` gated → `Exhausted`; a non-gate error from a proxied source, or the factory failing → `Error`. Later entries for the same source (through `create`, `create_async` or `aux_metadata`) record nothing. An ungated direct failure records nothing. Never log the sources (see the module's own warning about `Debug`).
